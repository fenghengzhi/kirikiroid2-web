## Mac Release O3 compiler-boundary 实证（2026-07-26；2026-08-02 重建）

这不是仅由 C++ 规则推演出的风险：修复前本地 Resource 分支保留未初始化 `size`，但又以裸
`tTJSVariant(data, size)` 把它作为无条件实参。旧 Mac Release O3 对象文件的实际反汇编中，
Clang 利用该未初始化读取的 UB 删除了 `chunkData == nullptr` gate，使原本应直接产生 null
Octet 的路径也落入 packed-table 解码。该旧产物与 Android `0x596874→0x596970` 的显式
null 分支相矛盾，因而必须在编译器边界上约束，而不能用“构造器运行时不会消费 length”
来假设优化器仍会保留 gate。

当前最终 Mac Release 对象
`out/macos/release/cpp/plugins/psbfile/CMakeFiles/psbfile.dir/main.cpp.o` 的 fresh
`objdump --disassemble --demangle` 已给出闭合实证（地址均为该 Mach-O 对象 `.text` 地址，
`CreateVariant_guess` 起点为 `0x600`）：

- `0x620` 读取 tag，`0x624` 的 `ARM64_RELOC_BRANCH26` 明确指向
  `PSB::detail::GetTypeCategory_guess(unsigned char)`；当前 O3 产物真实保留了恢复后的
  source-level classifier call（Android target 选择将其内联）。
- `0x684` 读取 `chunkData`，`0x688` 执行 `cbz x8, 0x8B8`；gate 已真实保留。
- `0x8B8` 以 `mov x0,#0` 建立 null Octet 指针，`0x8C4` 直接跳到 `0xA28` 的临时 Variant
  公共存储/CopyRef 路径。
- 该跳转绕过从 `0x690` 开始的 packed offsets/lengths 与 node index 解码，也绕过
  `0xA24` 带 `TJSAllocVariantOctet` relocation 的 allocator 调用；因此 null 路径不读取
  `size`、不解码 table、不分配。
- 同一对象的 `0x3CC`（`PropGet`）与 `0xC28`（`PropGetByNum`）也各有一条到同一
  classifier 的 `BR26` relocation，证明本轮新增的两个源码调用没有被本地 Release 编译器
  改写为另一套控制流。

这证明 `data != nullptr ? size : 0` 已闭合此前的 Clang O3 compiler-boundary。`size` 局部槽
本身仍未初始化，非空路径仍传递 helper 写出的原值；常量 `0` 只作为 null constructor 的
不消费 operand，不是对 Android 源码默认值或行为的改写。
