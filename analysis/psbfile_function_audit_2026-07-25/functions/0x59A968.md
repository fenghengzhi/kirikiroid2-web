## Android 归属与 fresh 证据

`disasm(addr="0x59A968", include_total=true)`、`xrefs_to`、vtable 原始值读取。
IDA 将该独立入口识别为 `0x59A968..0x59AA84`（69 条指令，正常返回点
`0x59AA14`，其后为异常展开清理）。关键证据如下：

- `xrefs_to(0x59A968)` 只有数据引用 `0x1A0B580`。fresh 读取相邻 vtable 槽得
  `[0x1A0B578, 0x1A0B580] = [0x59A8D8, 0x59A968]`，所以本函数是
  PSBFile typed-class autoreg 的第二虚槽（反注册），不是可静态枚举的 direct caller。
- `0x59A988` 从 `this+0x18` 读取 class name；`0x59A98C..0x59A998`
  构造 unregister-mode 的栈上 delegate/regist 状态，`classobj=null`、
  `hasCtor=false`、`isRegist=false` 均有显式零写入。
- `0x59A9A0` 直接调用 `PSBFile_ncb_registerMembers_guess@0x597F38`，即在
  unregister-mode 下重新执行同一 typed NCB 成员声明体。该 callee 只作本节点的
  调用上下文，本报告不替它审计内部三项 wrapper。
- `0x59A9A4..0x59A9DC` 取得全局 dispatch；非空时经 vslot `+0x60`
  调用 `DeleteMember(0, className, 0, global)`，忽略其普通返回状态，再经 vslot
  `+0x08` `Release()`；空指针时两步全部跳过。
- `0x59A9E8..0x59A9F4` 无条件把 class-info 的 `name/id/classObject/initialized`

  本函数反汇编也没有 `BL 0x597F08`。
- `0x59AA1C..0x59AA78` 是注册体抛异常时的 RAII 展开路径：再次执行同一
  global-delete/release/class-info-clear 序列后 `_Unwind_Resume`；清理本身在活动异常
  期间再抛则进入 terminate helper `sub_520FAC`。

因此 Android vtable/NCB/调用链归属为：`0x42CF28` 构造并挂入 class-autoreg
对象，后续通用反注册流程通过 vtable 第二槽 `0x1A0B580` vdispatch 到本函数；本函数
直接进入 `@597F38` 的 unregister-mode 成员声明体，作用域析构再删除全局 class 成员并

caller，不能把 vtable 数据引用伪装成 direct call。
